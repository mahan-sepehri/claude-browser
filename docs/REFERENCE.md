# Claude Browser — full reference

Everything Claude Browser does, in detail. For the overview and install steps see the [README](../README.md).

A browser panel in Cursor/VS Code that shows the same live tab Claude Code works in. You and Claude see and drive one tab, and you can pick elements into the prompt.

## How it works

```
 Cursor panel (webview) ──ws──┐
 another window's panel ──ws──┤
                              ├── engine (daemon/daemon.js) ── headless Chromium (tabs)
 Claude Code ── MCP stdio ────┘     127.0.0.1:47321, token in ~/.claude-browser/token
             (mcp/server.js)
```

- The **engine** starts on demand, from either the extension or the MCP server. It keeps running in the background and exits after 45 minutes with no viewers and no tool calls. The browser uses its own profile in `~/.claude-browser/profile`, so logins persist. The log is at `~/.claude-browser/engine.log`.
- **Its own browser**: the engine runs a "Chrome for Testing" build that it downloads once (about 200 MB) into `~/.claude-browser/chromium`, so no browser has to be installed. If Chrome, Edge or Brave is installed, it is used only until that download finishes. `claudeBrowser.browser: "system"` keeps using the installed one, and `claudeBrowser.chromePath` points at a specific executable. `node daemon/chromium.js install` fetches the build by hand (it falls back to the npmmirror CDN when Google's storage is unreachable).
- **Self-healing**: every 5 seconds the engine pings the browser. If it stops answering, or its process dies, the engine kills what is left, starts it again and reopens the same tabs. A page stuck in a loop gets a "This page isn't responding" bar with **Reload page**, which replaces the tab. The panel pings the engine too: if the engine itself hangs, the extension kills and replaces it. An engine older than the installed extension is replaced automatically, so no `pkill` is needed after an update. Open tabs are saved in `~/.claude-browser/session.json` and restored at the next start. **⋯ › Restart browser** does all of this on demand.
- The **panel** draws the browser's screencast and sends your mouse, wheel, keyboard (Persian included), paste and ⌘C/⌘X back. The viewport follows the panel's size, or a fixed device size picked from the 📱 menu.
- **Streaming**: Chrome is started at the pixel ratio the panel last reported (saved in `~/.claude-browser/display.json`; `renderScale` 1–3 in `config.json` fixes it), because headless Chrome's screencast ignores the emulated device scale and only follows the scale it was started with: a retina panel gets 2× frames pixel for pixel instead of a stretched 1× picture. After moving Cursor to a screen with another pixel ratio, **⋯ › Restart browser** applies it (the page is never emulated below the start scale, which would make Chrome report wrong frame sizes after a scroll). Frames are JPEG while the page moves and a lossless PNG still replaces the last one about 160 ms after it stops (the extra lossy frame Chrome sends right after a still is dropped, so the crisp one stays). The browser renders the next frame only when the panel has drawn the previous one, so there is never a backlog of stale frames. During a panel resize only the newest size is applied.
- **Side by side** (toolbar button with three bars): mobile 393×852, tablet 820×1180 and desktop 1280×800 at once, scaled to fit (or 50/75/100% with scrolling). The desktop one is the shared tab, the others are extra windows of the same browser, so they share the login. Going to another page or scrolling in any of them takes the others along (client-side route changes are replayed in place, not reloaded). Signing in or out in one pane changes the session they all share, so the others then load the page afresh instead (their in-memory app state would be stale); reload and “clear cookies & storage” apply to every pane, and panes load one after another rather than all at once. Clicks and typing stay in the pane you use; the label of the pane that has the keyboard is highlighted. Picking works in every pane and the report says which viewport it was. Chips in the bar choose which sizes to show. Each pane renders at the scale it is shown at (its device pixel ratio becomes panel ratio × fit scale), so Chrome draws text at the size you see instead of the panel shrinking a full-size picture; Claude's `viewports` screenshots are still captured at full size. Click the label above a pane (“Mobile · 393×852 ▾”) to give that device another size: presets (iPhone SE, small Android, iPad mini, 1024×768, Full HD, …), rotate, or a custom width × height. The choice is remembered. Claude can do the same with `browser_viewport({ sizes: { mobile: { width: 375, height: 667 } } })`. Claude gets all sizes in one call with `browser_screenshot({ viewports: true })`.
- **Errors to Claude**: the red badge counts the page's console errors and uncaught exceptions. Clicking it lists them (with the source line each came from); clicking one, or "Send all", puts an @-mention of the throwing line into the Claude prompt. Claude reads the full report with `browser_picked`: message, stack mapped through source maps to `file:line`, and the page's failed requests with their `browser_network` ids. `browser_console` also shows error stacks mapped to source.
- **Mark up the page** (toolbar button or ⌘⇧S): drag rectangles around areas or arrows towards things (⌥ switches tool for one stroke), type an optional note, press Enter. The screenshot with numbered marks is copied to the clipboard (paste it into the prompt), saved in `~/.claude-browser/screenshots`, and an @-mention of the first marked element's source line goes into the Claude prompt. `browser_picked` returns the image plus, per mark, the elements under it with their source lines, and the note. Works in each pane of the side-by-side view.
- **React inspector**: `browser_inspect({ pick, aspect: "react" })` and `browser_react` gives Claude the same for any element (ref, selector, text) or for a component by name, optionally with the component tree below it. Hook names need a dev build; values under keys that look like passwords or tokens are masked.
- **Right-click menu**: open link in a new tab or the default browser, copy link or image address, save image (to `~/Downloads`), copy the selection, back/forward/reload, **Send this element to Claude** (a pick without entering pick mode) and **Inspect element** (opens DevTools on that node). A page that shows its own context menu keeps it; hold Shift for this one.
- **Start page**: a new tab lists the web servers listening on this machine (with their page titles) and recent pages. Set `claudeBrowser.homeUrl` to open something else at start.
- **⋯ menu**: hard reload (⌘⇧R), screenshot to clipboard (also saved in `~/.claude-browser/screenshots`), copy URL, open in the default browser, zoom (⌘+ / ⌘− / ⌘0), light/dark appearance for `prefers-color-scheme`, clear cookies and storage for the site, restart browser. A red badge in the toolbar counts console errors on the page; clicking it opens DevTools.
- **Failed loads** keep the address you asked for in the URL bar (not `chrome-error://…`), so Enter or reload retries it.
- **DevTools** (toolbar button, ⌘⌥I or F12): the real Chrome DevTools for the shared tab (Console, Network, Elements, Sources…) in a resizable drawer, docked to the side or the bottom. The engine serves Chrome's built-in frontend and proxies its CDP socket, with the token in the path.
- **Pick** (crosshair button or ⌘⇧C in the panel): click an element. While picking, **↑** widens the highlight to the parent and **↓** narrows it back, **Shift-click** picks and stays in pick mode, **Esc** cancels. The engine decides the pick from the click position, so disabled controls, links, elements with `pointer-events: none` (icons inside buttons), open shadow DOM and same-origin iframes can all be picked, and the page never sees the click. The highlight follows scrolling and re-renders. Source maps are re-read after edits, so lines stay right after a file changes. A short **pick card** goes into the Claude Code prompt as an @-mentioned file (`~/.claude-browser/picks/pick-N.md`, about 100 tokens): what the element is (role, name, size, state), where it is on the page (landmarks, the heading it sits under, its place in a list), the page, and, when the page records it, the component and the source line where it is used. It works on any site and in any project, in VS Code and Cursor, with no tool call; nothing is sent as an image. Claude asks for more only when the task needs it with `browser_inspect({ pick: N, aspect })`: `styles` (the computed values that are set, ::before/::after, what changes on :hover and :focus), `rules` (authored CSS rules, winning declarations only, by stylesheet and line), `layout`, `animation` (running and declared animations, keyframes, libraries on the page; `ms` watches style changes, `scroll` scrolls the element through the viewport meanwhile), `events` (listeners and React handlers with code locations mapped to source), `html`, `react` and `source` (the component chain). The `claudeBrowser.onPick` setting can copy the card instead. The mention goes to the Claude Code session tab you used last in that window.
- **Address bar history**: pages you visit are saved to `~/.claude-browser/history.json`. Typing in the URL bar suggests them and completes the best match inline (origins like `localhost:5174` first). Use ↑/↓ to choose, Esc to dismiss, and Shift+Delete to remove the highlighted entry.
- **Tabs**: links with `target=_blank`, `window.open` popups (OAuth included) and ⌘T open new tabs. The strip appears once there are two or more tabs; middle-click or × closes a tab, and ⌘W closes it while more than one is open. You and Claude always share the active tab.
- **Native popups**: headless Chrome never paints `<select>`, date/time or color popups, so the panel draws its own: a dropdown list (mouse, arrow keys, Enter, typeahead) and the editor's native date/color pickers.
- **Uploads**: clicking a file input in the panel opens Cursor's file dialog. Claude uses `browser_upload`.
- **Downloads** are saved to `~/Downloads` (a unique name if the file exists). A toast reveals the file in Finder. Claude can list them with `browser_downloads`.
- **Camera & microphone**: the page uses your real devices. Local dev origins (localhost, 127.0.0.1, LAN IPs, `.local`) get them without asking. Any other site shows an Allow/Block bar in the panel, and "Remember" stores the choice in `~/.claude-browser/permissions.json`. A red **Camera · Mic** pill in the toolbar (and a dot on the tab) shows while a stream is live. Page audio plays through your speakers.
- **Source locations** need no project setup: React 19 keeps the creation stack of every element (`_debugStack`), and the engine maps those frames back to `file:line:col` through the dev server's source maps (`daemon/sourcemap.js`, works with Vite; webpack/Next maps are handled best-effort). React ≤18 `_debugSource` and `data-dev-src` attributes are still honoured if present. Without any of them, the report still has component names, text, styles and selector.

## Window mode (trial)

`"claudeBrowser.mode": "window"` runs the same engine with Chrome as a normal visible window instead of headless + streamed into the panel. The page is drawn natively, so it is always sharp, scrolls at the screen's frame rate, and native popups, prompts, file dialogs, IME and DevTools (⌘⌥I) are Chrome's own. Changing the setting restarts the browser.

- Tile the window next to Cursor. **Claude Browser: Open** (or the status bar item) brings it to the front; Chrome starts only when it is opened or Claude calls a tool.
- **Toolbar** (`daemon/ui.js`): a small floating bar in the page with Pick, Mark up, Side by side, Measure, Fill form, Sweep sizes, Open on my phone, the error badge, DevTools, Screenshot and ⋯ (hard reload, copy address, device size, light/dark, clear site data, restart, hide toolbar). Drag it by its grip; the position is remembered. ⌥⇧T hides it to a dot and back. It sits in the top layer inside a closed shadow root, so the page's styles can't touch it, and it is left out of every screenshot.
- **Toolbar clicks stay in the toolbar**: they don't bubble on to the page, so using the toolbar doesn't close the page's open menus (page listeners in the capture phase on window or document still see them).
- **Measure** (toolbar button with a ruler, or hold ⌥ anywhere): hover an element to see its size and its padding (green) and margin (orange) on each side, with the px value of every side; click one, then hover another to see the distance between them in px (red lines with labels), or from an element to the edges of the one around it. While measuring, clicks don't reach the page. Esc clears the chosen element, a second Esc ends it; releasing ⌥ ends the ⌥ version.
- **Fill this form** (toolbar button with lines and a pencil; `daemon/fill.js`): fills the form you used last (else the form with the most fields, else every visible field) with test data: names, phone numbers, IBANs with valid check digits, published test card numbers (Stripe and other test modes accept them), postal codes, emails, a password (`Test@12345`), dates, amounts within `min`/`max`, split code boxes, a choice in every select and radio group, every checkbox ticked. English data with international formats by default; on Persian pages (`lang="fa"`, or right-to-left with Persian text), Persian names and Iranian formats (mobile numbers, national IDs with their check digit, Sheba numbers). The menu also has **Fill with long text** (overflow testing) and **Clear the form**. Values are set with the native setter plus `input`/`change` (and a blur), so React and other frameworks see them.
- **Open on my phone** (toolbar button with a phone): a QR code of the current page with `localhost`/`127.0.0.1` swapped for this Mac's LAN address (`daemon/qr.js`, a small built-in encoder), the address, and Copy. The engine tries that address first; when the dev server only listens on localhost, the popover says so and how to start it with `--host` (Vite, Next.js, CRA). Pages that aren't local get a QR of their own address.
- **Sweep sizes** (toolbar button with two bars and arrows): the page goes smoothly from the window's size through common devices, widest first, as if you dragged the window smaller. Laptops: QHD 2560×1440, Full HD 1920×1080, MacBook Air 1440×900, Laptop 1280×800, the 1024×768 small laptop (those narrower than the window); then the height rises once to the largest tablet (iPad Pro 13″ 1024×1366) and shrinks through iPad Pro 11″ 834×1194 and iPad Air 820×1180 to iPad mini 744×1133; then rises once more to the largest phone (iPhone 16 Pro Max 440×956) and shrinks through 430×932, 412×915, 393×852, 390×844, 375×812 and 360×800 to the first iPhone SE 320×568. A tablet or phone that would need a second rise inside its group is left out (iPad 768×1024). It holds on each device for a moment with its name in the strip. The page is emulated at its real size, never scaled: a size taller than the window runs off its bottom. The strip above the toolbar shows width × height and has pause/resume, start again, slower/faster (¼× to 4× of 400 px/s along the path; the speed is remembered) and × to go back to the window's size. Switching tabs, picking a device size or turning on side by side ends it; it carries on across navigations.
- The tab in front is the shared tab: switching tabs in the window switches what Claude acts on, and tabs you open (⌘T, links) are adopted.
- The window's own size is the viewport. Device sizes from ⋯ or `browser_viewport` emulate inside the window; `browser_screenshot({ viewports: true })` with side-by-side off emulates mobile, tablet and desktop in turn and then gives the window its size back.
- **Pick**: the crosshair button, ⌥⇧P in the page, or **Claude Browser: Pick Element** in Cursor; click the element (Shift-click keeps picking, Esc cancels, ↑/↓ widen/narrow). The @-mention goes to the Cursor window focused last, through a small background connection the extension keeps to the engine.
- **Mark up** (button or ⌥⇧S): drag rectangles or arrows (⌥ switches), type a note, Enter. The picture with numbered marks goes to the clipboard and `~/.claude-browser/screenshots`; the report with the elements under each mark goes to Claude like a pick.
- **Errors**: the red badge lists the page's errors and failed requests; clicking one (or "Send all") sends it to Claude with the stack mapped to source.
- **DevTools**: the button opens Chrome's own DevTools docked to the tab (`Target.openDevTools`) and closes it again; ⌥⌘I works too.
- **Side by side** (button, ⌥⇧M, **Claude Browser: Side by Side**, or `browser_viewport({ multi: true })`): mobile, tablet and desktop **in the same tab**. The engine serves its side-by-side page (`daemon/shell.html`) in place of the tab's own document, at the page's own address (request interception of the top document only), and each pane is a same-origin iframe of the real page at its device size. So it is one tab with **one DevTools** for every pane (pick the pane in the Console's context menu), the address bar shows the page, and Back/Forward and typing a new address work for the whole view. The header row has the toolbar, chips to choose the devices, Fit/50/75/100% and Close; click a pane's label for other sizes (presets, rotate, custom). Panes follow the one you last clicked, scrolled or typed in: client-side route changes are replayed in place, a sign-in or sign-out in one pane reloads the others, and scrolling is mirrored proportionally. In-app navigation reaches every pane at once (within about 60ms). Full page loads (turning the view on, reloading, a sign-in) start one pane at a time: the next pane starts when the previous one has fired DOMContentLoaded and the tab has fewer than 400 requests open. All panes share one renderer process, so overlapping wouldn't be faster, and two copies of a dev-server app loading at once exceed the requests Chrome lets one process have in flight (`ERR_INSUFFICIENT_RESOURCES`). The pane tools act on loads first. A follower that needs a real reload gets a fresh iframe (new frame name) instead of a navigation, so the tab's history never refers to its old pages and Back moves only the pane in use. Claude's tools act on the widest pane (positions are mapped through the pane's scale); `viewports: true` captures each pane at its device size. **Touch** (header chip, on by default): the phone and tablet panes act as touch devices. They report an Android user agent (also on the page's own request), `maxTouchPoints`, `ontouchstart`, and `(hover: none)` / `(pointer: coarse)` both to `matchMedia` and in the page's CSS (media rules are rewritten, so Tailwind's `hover:` styles switch off). The mouse becomes a finger: touch and pointer events (`pointerType: "touch"`, implicit pointer capture), then the mouse events and click a phone sends after a tap; dragging scrolls with momentum (respecting `touch-action`) instead of selecting text; the cursor is a round dot. Chrome's own touch emulation is per tab, so this is done in the page (`emulateTouch` in `daemon/inpage.js`): events are synthetic (`isTrusted` is false, the click itself is the real one), and there is no pinch-zoom or pull-to-refresh. Limits: phone and tablet panes hide scrollbars (they overlay on devices); a page that refuses to be framed (X-Frame-Options, frame-ancestors) or navigates to another origin can't be followed there.
- Quitting the window (⌘Q) stops the browser; it starts again on the next Open or tool call.

## MCP tools

`browser_navigate`, `browser_screenshot`, `browser_snapshot`, `browser_click`, `browser_type`, `browser_press`, `browser_hover`, `browser_scroll`, `browser_wait`, `browser_evaluate`, `browser_console`, `browser_picked`, `browser_inspect`, `browser_viewport`, `browser_tabs`, `browser_upload`, `browser_select`, `browser_downloads`, `browser_status`, `browser_restart`, `browser_network`, `browser_react`, `browser_verify`

`browser_network` lists what the page requested (API calls and documents by default, failures always; filter by URL text or regex, method, status, type, or "since request N") and, with `id`, returns one request in full: headers, request body, response body (JSON pretty-printed) and timing. Bodies of API calls are captured as they finish, so they survive a navigation. `Authorization`, `Cookie` and similar header values are cut short unless `showSecrets` is passed.

`browser_verify` checks a code change in one call. It waits for the dev server's update to reach the page (read from its HMR websocket: Vite `update`/`full-reload`/`error`, webpack-dev-server `invalid`/`ok`/`errors`, Next.js `building`/`built`), lets the burst of updates, the requests they start and the DOM settle, then reports: the build error or error overlay if there is one; the element (`pick`, `ref`, `selector` or `text`) found again (same node, by selector, or after a reload by tag, name, role, component and place), with what changed in size, position, text, classes and computed styles, and before/after pictures of it; the optional `expect` text; and the console errors, exceptions and failed requests since the change (marked when they were there before it too). The "before" is taken when the element is picked, and every verify becomes the "before" of the next one. Without an element it returns a screenshot of the page; `viewports: true` adds one per device size. When no update arrives within `timeout` (8 s), it says so and checks the page as it is.

## MCP registration

The extension asks once to register its MCP server with Claude Code at user scope (or run **Claude Browser: Register MCP Server with Claude Code**). It points Claude Code at `~/.claude-browser/mcp-server.js`, a two-line file the extension rewrites on every start to load the installed version's `mcp/server.js`, so the registration survives updates. By hand:

```sh
claude mcp add --scope user claude-browser -- node ~/.claude-browser/mcp-server.js
```

## Build from source

```sh
git clone https://github.com/mahan-sepehri/claude-browser.git
cd claude-browser
npm install
./ship.sh   # packages claude-browser.vsix and installs it into Cursor or VS Code
```

Then run **Developer: Reload Window**. Bump `version` in `package.json` when the engine code changes: a running engine with a lower version is replaced on the next start, one with the same version is kept.

To try engine changes without touching the real browser, run a second engine in its own directory: `CLAUDE_BROWSER_HOME=/tmp/cb CLAUDE_BROWSER_PORT=47399 node daemon/daemon.js`, then open `http://127.0.0.1:47399/panel/panel.html?port=47399&token=$(cat /tmp/cb/token)` in any browser.

## Known limits

- One browser shared across all projects and windows; there's no per-project profile.
- Other permission prompts (location, notifications) aren't shown and default to denied.
- Headless Chrome can only capture with `--auto-accept-camera-and-microphone-capture`, so the Allow/Block gate is enforced by the injected page script (in every frame, on the prototype). A page deliberately working around it could still reach the devices. Treat this as a dev browser, not a hardened one.
- On macOS the browser is started through LaunchServices (`open -a`), so it has its **own** camera and mic permissions instead of those of whatever launched the engine. With the engine's own build, macOS asks once for "Google Chrome for Testing"; if it was denied, enable it in System Settings › Privacy & Security.
- Only with `claudeBrowser.browser: "system"`: macOS sees the engine as a second "Google Chrome" and may hand it things meant for your normal Chrome (links clicked in other apps, Dock reopen). The engine only adopts tabs opened by its own pages; anything else is closed and its URL passed to your normal Chrome. The engine's own build does not have this problem.
- The first start after switching between the installed Chrome and the engine's own build reuses the same profile. That works while both are the same major version; a profile last used by a newer browser may be reset by Chromium.
- Screencast streaming is as smooth as a remote view gets, not a native view: an extension cannot embed a real browser view the way Cursor's built-in browser does (that one is an Electron `WebContentsView` owned by the app itself).
